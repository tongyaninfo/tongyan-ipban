# ADR-0002 邮件通知与持久化发送

- 状态：接受
- 日期：2026-11-10
- 依据：用户在本会话确认通知设置方案、SQLite 三表迁移和凭据保护；登录通知限定主机登录事件，并要求后端 Resources HTML 模板、统一邮件标题前缀和发送历史。
- 相关：[通知接口合同](../api/README.md#邮件通知)、[变更日志](../../CHANGELOG.md)

## 背景

主机登录失败可能在短时间内大量产生。直接在采集、封禁或 HTTP 请求中发送邮件，会引入外部网络等待，并可能造成重复发送和邮件数量失控。通知还需要区分防火墙决定与实际执行结果，保留当时的邮件内容，不能使用当前配置重建历史事实。

## 决定

### 事件来源与进程分工

Agent 在新增主机登录证据、写入防火墙动作时，与原业务记录同事务保存通知候选。登录证据实际插入零行时不生成候选，唯一事件键为 `login:{id}` 或 `firewall:{id}`。四类事件为 `loginSuccess`、`loginFailure`、`ban`、`unban`，不包含管理台账号登录。

配置默认关闭。事件必须晚于当前启用周期的 `enabledSinceUtc`，且发生时间不早于 `min(queueLifetimeHours, 24)` 小时前；不为启用前或超龄历史事件补发通知。关闭总开关或对应规则时不生成候选。

API 后台任务负责聚合、领取、投递和维护队列，使用 MailKit 连接已配置的 SMTP 服务。它不是自建接收邮件服务器。Agent 不连接 SMTP、不解密邮件授权码；纯函数判定引擎保持原有边界。API 停止时暂停邮件投递，恢复后处理仍有效的持久化任务。

### 存储与凭据

配置复用 `system_settings`。本会话已授权新增 SQLite v7 正向迁移，不重写 v1–v6，不给历史业务表增列：

| 表 | 职责 |
| --- | --- |
| `notification_events` | 唯一来源键、最小事件快照、配置修订号、聚合分组和处理状态 |
| `notification_outbox` | 每个收件人独立任务、已渲染正文与模板版本、稳定 Message-Id、发送状态、重试和租约 |
| `notification_rate_state` | 全局固定窗口计数、每来源聚合间隔及候选超限计数 |

授权码使用 AES-GCM 加密，密文与普通配置分开保存；读取配置只返回 `hasCredential`。密钥文件 `notifications-key-protection.bin` 独立于 SQLite，限制为 API 服务账号访问，不能假定 SQLite 备份同时包含该文件。恢复凭据需要对应的数据库与密钥文件。密钥丢失后不自动生成替代密钥解密旧数据；必须显式清除旧凭据后重新配置。页面提供带二次确认的清除入口，要求先关闭通知并保存全部修改。

配置更新带 `revision`，冲突返回 409；更新与可靠审计同事务提交。更新配置会取消旧的 `pending` 候选和 `queued`、`retry` 发件任务，保留已发送快照。总开关关闭后，管理员仍可显式发送测试邮件。

### 频率、容量与重试

默认全局额度为每分钟 10 次、每小时 60 次，按 SMTP 投递尝试计数，包含重试和测试。窗口状态持久化，服务重启不清零。窗口从首次领取任务开始计时，不是任意滑动时间段。登录事件为低优先级，最多使用窗口额度的 80%（向下取整，最低 1 次）；封禁、解封和测试可使用剩余额度，但仍受全局上限约束。

每来源聚合规则如下；首批可立即生成邮件，后续候选等待配置的合并间隔。默认间隔分别为 300、600、60、60 秒，允许设置 10–86400 秒。

查询先排除冷却中的分组再分页，避免热门来源阻塞新来源。某组仍有待投递任务时继续累计候选，不再生成该组的积压邮件。除聚合时间外，还持久化每组、每收件人的实际发送时间；额度或 SMTP 恢复后不会连续补发同组通知。

| 类型 | 聚合分组 |
| --- | --- |
| 登录成功 | 类型、规范化来源 IP、协议、用户名 |
| 登录失败 | 类型、规范化来源 IP、协议 |
| 封禁、解封 | 类型、规范化来源 IP |

待处理候选最多 10000 条，达到 8000 条后不再接收登录通知候选，为封禁/解封保留余量。超限仍保存原业务记录，并按四种固定类型累计可见的抑制数量，不淘汰业务日志。待发任务最多 1000 条，登录通知最多占用 800 个待发槽位。摘要统计分组内全部待处理事件，正文及历史详情保存前 100 条样本，HTML/纯文本表格最多展示 20 条，避免邮件随攻击流量无限增长。

每个收件人独立发送、独立重试，不因部分收件人失败重新发送已成功的任务。默认最多重试 3 次，可设置 0–5 次；暂时性失败按 1、5、15 分钟退避，后续重试继续使用 15 分钟。认证、证书或配置等永久性错误不自动重试。发送任务使用 2 分钟租约，恢复过期租约不会重新执行任何防火墙动作。恢复仍受重试预算和任务有效期限制，预算或有效期耗尽时标记 `failed / SMTP_DELIVERY_UNCERTAIN`，明确结果无法确认，不把未知投递结果称为没有发送。

队列有效期默认 24 小时，可配置 1–168 小时；通知记录默认保留 30 天，可配置 1–365 天。已发送记录按 SMTP 接收时间计算留存，避免排队多天后刚发送就被清理；其他已结束任务按创建时间计算。来源事件的最多 24 小时过滤与已经入队任务的有效期是两个不同限制。后台分批清理过期的已完成数据。

### 邮件模板与状态语义

模板放在 `backend/src/IpBan.Api/Resources/EmailTemplates/`，以嵌入资源随发布包提供。共享布局和四类事件、摘要、测试模板同时生成 HTML 与纯文本；事件字段编码后填入，标题固定以 `通研IPBan-` 开头。历史详情读取发送任务保存的正文、模板版本和事件样本，不重新渲染。

`Applied` 才能表示已封禁，`Removed` 才能表示已解封；`Failed`、`Disabled` 明确提示未生效或失败。到期邮件依赖实际解封结果，不能仅按预计到期时间宣称已解封。发送状态 `sent` 仅表示 SMTP 服务已接受邮件，不能证明收件箱送达。

SMTP 接受邮件和本地数据库标记不能原子提交。任务使用稳定 Message-Id 帮助追踪，但不承诺 exactly-once；崩溃恢复可能极少量重复投递。

## 影响与边界

SQLite v7 升级沿用现有备份、锁与事务机制，旧 Agent 遇到更高版本数据库会拒绝启动。需要回退时，应停服务后按经授权的恢复流程恢复升级前备份，不执行降级迁移。

本功能不修复既有内存到期解封调度，不能推导为重启后会补做解封。SMTP 不可用不触发防火墙重试或业务动作恢复。真实 SMTP、Windows/Linux 正式发布及服务器部署需要独立验收；本轮本地测试结果维护在根 [变更日志](../../CHANGELOG.md)。
